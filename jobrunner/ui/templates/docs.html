Guide jobrunner

jobrunner exécute des jobs Python (des DAG de tâches) déclenchés par API REST, par cron, depuis la GUI, ou via des endpoints HTTP personnalisés. Un job est un simple fichier .py éditable dans le navigateur : rien à déployer, rien à redémarrer.

Le cycle de vie complet : Jobs → New job → écrire le code → Save → Trigger → suivre le run dans Runs.

Créer un job

Un fichier par job, dans le répertoire des jobs. Suppression via le bouton Delete de la page Jobs ou du job (l'historique des runs est conservé). Le nom du job = nom du fichier (etl_daily.py → job etl_daily). Attributs de module optionnels :

{% set doc %} """Mon premier job""" from jobrunner.dsl import task description = "Ce que fait ce job" # affichée dans la GUI schedule = "0 2 * * *" # cron optionnel (tous les jours à 2h) default_params = {"env": "dev"} # fusionnés avec les params du trigger @task def hello(ctx): ctx.log("bonjour") # écrit dans le log de la tâche return {"rows": 42} # valeur transmise aux tâches suivantes {% endset %}

Tâches & DAG

Chaque fonction décorée @task est une tâche. Les dépendances définissent le graphe ; les tâches indépendantes d'un même niveau s'exécutent en parallèle. La valeur de retour d'une tâche amont est injectée par nom de paramètre :

{% set doc %} @task def extract(ctx): return {"rows": 1000} @task(depends_on=[extract]) def transform(ctx, extract): # ← reçoit le retour de extract() return {"rows": extract["rows"] * 2} @task(depends_on=[transform]) def load_warehouse(ctx, transform): ... @task(depends_on=[transform]) def load_marts(ctx, transform): # en parallèle avec load_warehouse @task(depends_on=[load_warehouse, load_marts]) def notify(ctx): ... # ne part que quand les deux ont fini {% endset %} 
{{ doc | trim | forceescape }}
  • Si une tâche lève une exception : la tâche est failed, ses descendantes upstream_failed, le run failed — la traceback est dans le log de la tâche.
  • Les print() et ctx.log() sont capturés par tâche, visibles en direct dans la page du run.

Modules partagés (Libraries)

Le code commun à plusieurs jobs/endpoints se place dans jobs/lib/ : créez et éditez ces modules depuis la page Libraries, puis importez-les normalement — ils sont sur le sys.path de tous les processus et rechargés à chaud :

# jobs/lib/my_utils.py
def normalize(name: str) -> str:
    return name.strip().lower()

# dans un job ou un endpoint :
from my_utils import normalize

@task
def clean(ctx):
    ctx.log(normalize(ctx.params.get("name", "")))

@endpoint("who")
def who_handler(ctx):
    return {"hello": normalize(ctx.params.get("name", "world"))}

Dans l'éditeur, F12 sur my_utils ouvre sa source et my_utils. propose ses membres en autocomplétion.

Déclencher avec des paramètres surcharge les valeurs par défaut : {"params": {"date": "2026-11-11"}}

Cron (schedule)

schedule = "*/15 * * * *" au niveau module — format cron classique « minute heure jour mois jour-de-semaine » (UTC). Le planificateur tourne chaque minute et rattrape les occurrences manquées (sans rattrapage au premier démarrage). Désactivable globalement avec JOBRUNNER_ENABLE_BEAT=false.

Déclencher un run

Trois façons : bouton Trigger run sur la page du job, cron, ou l'API :

Tokens : page API tokens. Documentation interactive des routes : /api/docs.

Endpoints HTTP personnalisés

Un job peut exposer ses propres routes API avec @endpoint("chemin") — exécution synchrone dans le worker, la valeur retournée devient la réponse JSON :

{% set doc %} from jobrunner.dsl import endpoint @endpoint("deploy") # → POST/GET /api/v1/web/mon_job/deploy def deploy_handler(ctx): env = ctx.params.get("env", "dev") # body JSON (POST) ou query params (GET) ctx.log(f"deploy vers {env}") return {"deployed": True, "env": env} {% endset %} 
{{ doc | trim | forceescape }}
  • Gérez-les comme les jobs : page Endpoints (créer, éditer, tester, supprimer — seule la fonction de l'endpoint est retirée du fichier, le reste est préservé à l'octet près).
  • Codes de réponse : 200 succès · 404 job/endpoint inconnu · 500 exception (traceback dans log) · 504 timeout.
  • Retourner autre chose que du JSON — une page HTML complète, du texte, un statut personnalisé : html() / text() (ci-dessous).
  • Endpoint public (sans token) : @endpoint("chemin", public=True) — badge « public » orange dans la GUI. ⚠️ À réserver aux données réellement publiques.
  • Limiter la méthode HTTP : methods=("GET",) — l'endpoint n'accepte que GET ; un POST reçoit 405 Method Not Allowed (avec l'en-tête Allow). Défaut : GET + POST. Le sélecteur du panneau Test s'adapte automatiquement.
  • Le handler peut déclencher le DAG du job lui-même : voir run-now dans l'exemple etl_daily.

Retourner une page HTML (ou du texte)

{% set doc %}from jobrunner.dsl import endpoint, html, text @endpoint("report") def report_handler(ctx): rows = ctx.params.get("rows", 1000) return html(f""" Rapport

Rapport ETL

{rows} lignes traitées — run {{ '{' }}ctx.run_id[:8]{{ '}' }}

""") @endpoint("health-text", public=True, methods=["GET"]) # public, GET seulement def health_text(ctx): return text("OK\n", status=200, headers={"X-Custom": "yes"}) {% endset %} 
{{ doc | trim | forceescape }}

Le navigateur reçoit directement la page (Content-Type text/html) ; le statut HTTP et les en-têtes sont personnalisables. Chaque appel reste tracé dans l'historique, et l'en-tête de réponse X-Jobrunner-Run-Id y renvoie.

Packages Python

La page Packages installe des librairies supplémentaires (pandas>=2.0, requests[socks]…) directement depuis la GUI. Elles sont disponibles immédiatement dans les jobs et survivent aux reconstructions du conteneur. Dépôt pip et proxy (avec auth) configurables : variables JOBRUNNER_PIP_INDEX_URL / JOBRUNNER_PIP_PROXY ou surcharge GUI.
